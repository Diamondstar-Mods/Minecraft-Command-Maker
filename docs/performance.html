Performance Tips

Keep Command Maker running smoothly with these performance guidelines. While the mod is designed to be lightweight, certain patterns can impact server TPS and responsiveness.

Understanding Command Maker's Performance Profile

Command Maker adds negligible overhead during normal operation. Alias lookups use an in-memory hash map, variable substitution is O(n) relative to command length, and syntax matching runs once per invocation. The vast majority of performance impact comes from what your aliases do -- not from the mod itself.

Operation Performance Cost Notes
Alias lookup Negligible (O(1)) Hash map in memory
Variable substitution Negligible Scales with command length
Syntax matching Minimal One regex pass per pattern
File I/O (reload) Moderate spike Only during /cmd reload
Heavy commands in alias Depends on command Not the mod's fault

Excessive Alias Chains

The Problem

One alias calling another, which calls another, creates a chain. While Command Maker supports this, deep chains add latency because each alias must be resolved, substituted, and dispatched individually.

Example of a Problematic Chain

// Alias 1: /welcome
/welcome: give_player_kit

// Alias 2: /give_player_kit
/give_player_kit: give_player_items

// Alias 3: /give_player_items
/give_player_items: give ${player} diamond 1 && broadcast_welcome

// Alias 4: /broadcast_welcome
/broadcast_welcome: say Welcome ${player}!

Each link in this chain requires a separate dispatch cycle. Running /welcome triggers four lookups and four command dispatches.

Better Approach

// Consolidate into a single alias:
/welcome: give ${player} diamond 1 && say Welcome ${player}!

Guidelines for Chains

  • Limit chains to 2-3 aliases maximum for frequently-used commands
  • Consolidate simple sequences into a single alias with &&
  • Use functions for complex sequences -- a single /function call is more efficient than chained aliases
  • Profile before optimizing -- a chain used once per hour is not worth consolidating

Function File Size

How Functions Work

Command Maker's function system (function:name aliases) reads .mcfunction files from the Functions directory. Each file can contain multiple lines, and each line is executed sequentially by the Minecraft command engine.

Size Recommendations

File Size Performance Impact Recommendation
Under 20 lines Minimal Ideal for most use cases
20-100 lines Noticeable on slower hardware Fine for admin or infrequent use
100-500 lines Can cause tick lag Split into smaller functions
500+ lines Severe TPS drops Restructure or use scheduled execution

Best Practices for Functions

  • Break large functions into smaller, focused files
  • Use /schedule to spread heavy function execution across multiple ticks
  • Avoid loops in functions that run more than a few iterations per tick
  • Comment your functions to identify sections that could be optimized later

Reloading: /cmd reload Best Practices

What Happens During Reload

When you run /cmd reload, Command Maker:

  1. Reads aliases.json from disk
  2. Reads syntax.json from disk
  3. Reads permissions.json from disk
  4. Reads variables.json from disk
  5. Parses all JSON files
  6. Rebuilds the in-memory alias map
  7. Re-registers all alias commands with Brigadier
  8. Rebuilds the syntax pattern matcher

This is a synchronous operation -- the server thread waits until it completes.

Guidelines

  • Avoid frequent reloads on production servers with many aliases (500+). Each reload can take several hundred milliseconds.
  • Schedule reloads during low-traffic periods or announce them to players
  • Test configuration changes on a local or test server before reloading on production
  • Monitor chat for errors after reload -- JSON parsing errors are logged to console
  • Consider a rolling reload approach for very large configurations: break aliases into multiple files if supported

Warning

Frequent /cmd reload on large configurations can cause noticeable lag spikes. Never use reload in a repeating command block or automated loop.

Selector Performance: @e in Repeating Command Blocks

Why @e Is Expensive

The @e selector targets every entity in the world -- mobs, players, items, minecarts, armor stands, area effect clouds, and more. On a typical server, this can be hundreds or thousands of entities. Using @e in an alias that runs every tick (via repeating command block or function) is one of the fastest ways to degrade server performance.

Selector Performance Comparison

Selector Typical Targets Relative Cost
@s 1 (the executor) Free
@p 1 (nearest player) Very cheap
@a Players only (usually 1-100) Cheap
@e[type=minecraft:creeper] Filtered entities Moderate
@e (unfiltered) All entities (potentially thousands) Expensive
@e[distance=..10] Nearby entities Less expensive than unfiltered

Best Practices for Selectors

  • Always filter @e with type, distance, or tag parameters: @e[type=minecraft:zombie, distance=..50]
  • Prefer @a over @e[type=player] -- it is optimized specifically for players
  • Use @s when possible -- it requires no entity scanning at all
  • Avoid @e in command blocks or functions that run more than once every few seconds
  • Use scoreboard tags to track specific entities instead of scanning for types

JSON File Size Considerations

The Impact of Large JSON Files

Command Maker reads JSON configuration files only on server startup and during /cmd reload. However, very large files can cause:

  • Longer reload times (visible lag on the server)
  • Higher memory usage (the entire file is parsed into memory)
  • Increased risk of JSON syntax errors (harder to find in large files)

Recommended Limits

File Recommended Max Size Max Aliases/Entries
aliases.json 500 KB ~2000 aliases
syntax.json 100 KB ~500 patterns
permissions.json 100 KB ~1000 permission entries

Tips for Managing Large Configs

  • Use comments sparingly -- JSON doesn't officially support comments, so they may increase file size without benefit
  • Minify JSON for production use -- remove unnecessary whitespace from large files
  • Split logically -- group related aliases together and use section comments
  • Avoid duplicate entries -- they waste space and can cause confusing behavior
  • Remove unused aliases periodically with /cmd remove or the GUI

Pro Tip

Use a JSON formatter with syntax highlighting (like VS Code) to manage large alias files. The built-in folding and search make navigation much easier.

Caching Behavior

What Command Maker Caches

  • Alias map: Loaded at startup and on reload. All aliases are held in memory as a hash map for O(1) lookup.
  • Syntax patterns: Compiled regex patterns are cached. No recompilation happens between reloads.
  • Permission data: Permission levels are cached per player until reload or permission change.
  • Custom variables: Loaded into memory at startup. Variable substitution is instant.

What Is NOT Cached

  • Function files: Each function:name alias reads the .mcfunction file from disk. For frequently-used function aliases, this means repeated disk I/O.

Optimizing Function Alias Performance

If you use function-based aliases frequently, consider these strategies:

  • Convert frequently-used functions to regular aliases (inline the commands)
  • Use Minecraft's built-in /function command in a datapack instead of Command Maker functions for core server mechanics
  • Reserve function aliases for dynamic or user-uploaded content that changes often

Impact on Server TPS

Measuring TPS Impact

Use the /cmmakerperm debug features or server profiling tools to measure Command Maker's actual TPS impact:

# Check current TPS
/debug start
/debug stop
/debug report

Common TPS Impact Patterns

Pattern TPS Impact Solution
@e in repeating alias High (5-10 TPS drop) Use filtered selectors
1000+ aliases + frequent reloads Spike during reload Reload during off-peak
Large function files run every tick High Spread execution with /schedule
Alias chains (5+ deep) Low-moderate Consolidate into single alias
Simple aliases with /say or /tp Negligible No action needed

Performance Monitoring Tools

  • Spark -- The most popular Minecraft server profiler. Use /spark profiler start to identify lag sources.
  • Observable -- Built-in Minecraft performance monitoring with /debug commands.
  • Timings -- Paper/Pufferfish timing reports show per-command execution time.
  • Server log analysis -- Check for warnings about Can't keep up! messages.

Performance Checklist

Quick Reference

  • Keep alias chains short (2-3 max)
  • Consolidate simple command sequences with &&
  • Limit function files to under 100 lines
  • Always filter @e with type/distance/tag
  • Use @s instead of @p or @a when the executor is the target
  • Reload during off-peak hours only
  • Keep aliases.json under 500 KB
  • Remove unused aliases regularly
  • Profile before optimizing -- measure, don't guess
  • Use Spark or similar tools to identify real bottlenecks
