Advanced Syntax Patterns

Custom syntax patterns are the heart of Command Maker's power. This guide covers advanced techniques for building flexible, robust command patterns that handle real-world server needs.

If you are new to syntax patterns, read the Custom Syntax System overview first, then return here for the advanced details.

Pattern Structure Refresher

Every syntax pattern is an entry in syntax.json with three parts:

{
  "pattern_name": {
    "pattern": "/command <param1> <param2>",
    "description": "What this pattern does"
  }
}

The pattern string starts with / followed by the command name and any parameters in angle brackets. When a player types a command that matches the pattern, the captured parameters become available as variables in your aliases.

Greedy Parameters

A greedy parameter captures everything from its position to the end of the command, including spaces. This is essential for parameters that contain free-form text like messages, reasons, or descriptions.

How Greedy Works

The last parameter in a pattern is automatically greedy. Consider this pattern:

{
  "msg": {
    "pattern": "/msg <player> <message>",
    "description": "Send a private message"
  }
}

When a player types /msg Steve hey, how are you?, the pattern captures:

  • <player> → Steve
  • <message> → hey, how are you? (everything after Steve)

The alias variable ${msg_message} contains the full message text including spaces.

Multi-Word Greedy Example

{
  "ban": {
    "pattern": "/ban <player> <reason>",
    "description": "Ban a player with a detailed reason"
  }
}
/cmd add ban ban ${ban_player} ${ban_reason} && say ${ban_player} was banned for: ${ban_reason}

Typing /ban Steve griefing the spawn area bans Steve with the full reason griefing the spawn area. Without greedy behavior, only the first word would be captured.

Greedy Limitation

Only the last parameter in a pattern is greedy. If you have three parameters, only the third one captures multi-word input. Parameters before the last capture only single words.

Multi-Parameter Patterns

You can define patterns with two, three, or more parameters for complex commands.

Two Parameters

{
  "tpcoord": {
    "pattern": "/tpcoord <x> <z>",
    "description": "Teleport to specific X and Z coordinates"
  }
}

Creates variables: ${tpcoord_x} and ${tpcoord_z}.

/cmd add tpxz execute in minecraft:overworld run tp ${player} ${tpcoord_x} 64 ${tpcoord_z}

Three Parameters

{
  "giveitem": {
    "pattern": "/giveitem <player> <item> <amount>",
    "description": "Give an item to a player with a specific count"
  }
}

Creates variables: ${giveitem_player}, ${giveitem_item}, and ${giveitem_amount}.

/cmd add giveitem give ${giveitem_player} ${giveitem_item} ${giveitem_amount}

Four Parameters

{
  "editwarp": {
    "pattern": "/editwarp <name> <x> <y> <z>",
    "description": "Set a warp point at specific coordinates"
  }
}

Creates variables: ${editwarp_name}, ${editwarp_x}, ${editwarp_y}, ${editwarp_z}.

/cmd add setwarp setblock ${editwarp_x} ${editwarp_y} ${editwarp_z} minecraft:beacon && say Warp ${editwarp_name} created!

Optional Parameters Concept

Command Maker does not natively support truly optional parameters in syntax patterns. A pattern matches only when exactly the right number of space-separated tokens is provided. However, you can work around this with multiple patterns.

Workaround: Multiple Patterns for Overloads

Define two separate patterns that share the same alias target:

{
  "kick_reason": {
    "pattern": "/kick <player> <reason>",
    "description": "Kick a player with a reason"
  },
  "kick_default": {
    "pattern": "/kick <player>",
    "description": "Kick a player with default reason"
  }
}

Then create two aliases (or use a .mcfunction file to handle both cases):

/cmd add kick_reason kick ${kick_reason_player} ${kick_reason_reason}
/cmd add kick_default kick ${kick_default_player} "No reason given"

Pattern Matching Priority

When a player types a command, Command Maker tries patterns in the order they appear in syntax.json. The first matching pattern is used. More specific patterns (with more parameters) should come before less specific ones.

Pattern Naming Conventions

Good naming makes your patterns readable and maintainable. Follow these conventions:

Convention Good Example Bad Example
Use lowercase tpa TPA_REQUEST
Describe the action warpplayer wp
Underscore for readability ban_with_reason banwr
Match the command name Pattern /tp with name tp Pattern /tp with name teleportation
Be consistent across patterns tpa, ban, kick tpa, player_ban, kick_user

Consistent naming matters because the pattern name becomes part of the variable name. A pattern named ban_with_reason with parameter <player> creates the variable ${ban_with_reason_player}. Keep pattern names short but descriptive enough that the full variable name remains readable.

Combining Syntax with Variables

The real power of Command Maker comes from combining syntax parameters with built-in and custom variables in a single alias.

Syntax Parameter + Built-in Variable

{
  "tpa": {
    "pattern": "/tpa <player>",
    "description": "Request to teleport to a player"
  }
}
/cmd add tpa say ${player} wants to teleport to ${tpa_player} at coordinates ${tpa_player}'s location!

Here, ${player} is the built-in variable for the command sender, and ${tpa_player} is the syntax parameter from the tpa pattern.

Syntax + Custom Variable

/setcmdvariable server_prefix ">>>"
{
  "broadcast": {
    "pattern": "/broadcast <message>",
    "description": "Broadcast a message"
  }
}
/cmd add broadcast say ${server_prefix} ${broadcast_message}

When you run /broadcast Server restarting soon!, it outputs: >>> Server restarting soon!

All Three Combined

{
  "report": {
    "pattern": "/report <player> <reason>",
    "description": "Report a player for breaking rules"
  }
}
/cmd add report say [REPORT] ${player} reported ${report_player} for: ${report_reason} at ${x}, ${y}, ${z}

Running /report Steve griefing produces: [REPORT] Alex reported Steve for: griefing at 123, 45, -789. This combines the sender's name (built-in), the target and reason (syntax parameters), and the sender's location (built-in coordinates).

Pattern Validation Tips

Debugging syntax patterns can be tricky. Use these tips to ensure your patterns work correctly.

Issue Check Solution
Pattern does not match Does the player's input start with /? Make sure the pattern string starts with /. Patterns without the leading slash will not match chat input.
Wrong parameter captured Are parameter names unique within the pattern? Each parameter name in a pattern must be unique. Duplicate names cause unpredictable capture behavior.
Multi-word value not captured fully Is this the last parameter? Only the last parameter is greedy. If you need a multi-word parameter in the middle, restructure the pattern so the free-text field comes last.
Variable returns empty Does the variable name match the pattern? Variable format: ${patternName_paramName}. Both must be lowercase and spelled exactly as defined in syntax.json.
Pattern conflicts with another Do two patterns start with the same prefix? A pattern /msg <player> <msg> and /msg <msg> both match inputs starting with /msg. Make patterns unambiguous or reorder them.
JSON parse error Is the syntax.json valid JSON? Use a JSON validator. Common issues: trailing commas, missing quotes, unescaped quotes inside strings.

Testing Checklist

Before deploying a new pattern on your live server, run through this checklist:

  1. Add the pattern to syntax.json and run /cmd reload.
  2. Run /syntax to verify the pattern appears in the list.
  3. Type the pattern's command with sample parameters and verify the alias executes.
  4. Test edge cases: single-word parameters, multi-word (greedy) parameters, special characters.
  5. Test with a non-operator player to check permission behavior.
  6. Verify that the alias output uses all captured variables correctly.

Debugging with Tellraw

When debugging patterns, create a simple alias that echoes the captured variables back to you:

/cmd add debugpattern say Param1: ${mypattern_param1}, Param2: ${mypattern_param2}

This lets you see exactly what each parameter captured.

Real-World Pattern Examples

Warp System with Description

{
  "warp": {
    "pattern": "/warp <name>",
    "description": "Warp to a named location"
  }
}
/cmd add warp tp ${player} ${warp_name} && say Warped to ${warp_name}!

Economy Pay System

{
  "pay": {
    "pattern": "/pay <target> <amount>",
    "description": "Pay another player"
  }
}
/cmd add pay say ${player} paid ${pay_target} ${pay_amount} coins!

Server Shop Order

{
  "order": {
    "pattern": "/order <item> <quantity> <delivery_location>",
    "description": "Order items from the server shop"
  }
}
/cmd add order say ${player} ordered ${order_quantity}x ${order_item} delivered to ${order_delivery_location}

Typing /order diamond 64 spawn_tower results in: Alex ordered 64x diamond delivered to spawn_tower.
