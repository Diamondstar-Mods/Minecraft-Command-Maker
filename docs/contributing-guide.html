Contributing Guide

Thank you for your interest in contributing to Command Maker! This guide will walk you through everything you need to know to get started as a contributor, from setting up your development environment to submitting your first pull request.

Quick Links

  • GitHub Repository: github.com/nekromancer/Minecraft-Command-Maker-3
  • Issues Tracker: github.com/nekromancer/Minecraft-Command-Maker-3/issues
  • Discord: Join the community for discussions and support

Getting Started

Prerequisites

Before you begin contributing, make sure you have the following installed:

  • Java Development Kit (JDK): Version 17 or 21+ for modern modules, Java 8 for legacy modules. See the version matrix below.
  • Git: For version control and submitting pull requests.
  • An IDE: IntelliJ IDEA (recommended), Eclipse, or VS Code with Java extensions.
  • A GitHub account: For forking the repository and submitting PRs.

Setting Up the Development Environment

Step 1: Fork and Clone

  1. Navigate to the Command Maker repository on GitHub.
  2. Click the Fork button in the top-right corner to create your own fork.
  3. Clone your fork locally: 
    git clone https://github.com/YOUR_USERNAME/Minecraft-Command-Maker-3.git
cd Minecraft-Command-Maker-3
  4. Add the upstream repository to keep your fork in sync: 
    git remote add upstream https://github.com/nekromancer/Minecraft-Command-Maker-3.git

Step 2: Create a Branch

Command Maker follows a specific branch naming convention. Create a branch based on what you are working on:

# New features
git checkout -b feature/my-awesome-feature

# Bug fixes
git checkout -b fix/description-of-bug

# Documentation
git checkout -b docs/my-docs-change

# Refactoring
git checkout -b refactor/module-name

Step 3: Import the Project

IntelliJ IDEA (Recommended):

  1. Open IntelliJ IDEA.
  2. Select File > Open and navigate to the cloned directory.
  3. Select the build.gradle file and click Open as Project.
  4. IntelliJ will automatically detect the Gradle wrapper and import dependencies.
  5. If prompted, trust the Gradle project and allow it to download dependencies.

Step 4: Build the Project

Command Maker uses Gradle for building. The project includes a Gradle wrapper, so you don't need Gradle installed globally.

# Build all active modules
./gradlew build

# Build a specific module
./gradlew :server-1.21:build

# Build the latest server version
./gradlew :server-1.22:build

# Build and run the client
./gradlew :client:runClient

# Clean build artifacts
./gradlew clean

Gradle JDK Configuration

JDK paths are configured in gradle.properties. If you have JDK installed at a different location, you may need to update these paths. Look for properties like org.gradle.java.home or custom JDK path entries in the file.

Finding Issues to Work On

Looking for a place to start? Here is how to find good first issues:

  1. Browse the Issues Tracker.
  2. Look for labels like good-first-issue, help-wanted, or bug.
  3. Comment on the issue to let others know you are working on it.
  4. If you have an idea for a new feature, open a new issue first to discuss it with the community.

Good First Contributions

If you are new to the project, consider these types of contributions:

  • Documentation improvements: Fix typos, clarify instructions, add examples.
  • Bug fixes: Small, well-scoped bugs are great for getting familiar with the code.
  • Test coverage: Adding unit tests for existing functionality.
  • Code cleanup: Removing unused imports, improving Javadoc, fixing formatting.

Coding Standards

Command Maker follows these code conventions to maintain consistency across the codebase:

Java Style

  • Naming: Use camelCase for variables and methods (myVariable, doSomething()). Use PascalCase for classes (AliasManager, CommandSyntax).
  • Indentation: Use 4 spaces or 1 tab per indent level.
  • Line length: Maximum 120 characters per line.
  • Braces: Use K&R style (opening brace on the same line):
public class Example {
    public void method() {
        if (condition) {
            doSomething();
        } else {
            doSomethingElse();
        }
    }
}

Documentation

  • All public classes and methods should have Javadoc comments.
  • Use @param, @return, and @throws tags where applicable.
  • Keep comments clear and concise; avoid stating the obvious.
  • Update documentation when you change behavior.

Commit Messages

Follow the existing commit message convention:

  • Start with a verb: Add, Fix, Update, Improve, Remove.
  • Keep the first line under 70 characters.
  • Add a blank line followed by details if needed.
Add warp system with set, go, and list commands

- /setwarp, /warp, /warps commands via syntax system
- Persistent storage in warps.json
- Permission checks for admin-only operations
- Tab completion for warp names

Testing Your Changes

Building

Always ensure the project builds successfully before submitting a pull request:

./gradlew :server-1.21:build

Running the Client

For client-side changes, launch the Minecraft client with your mod:

./gradlew :client:runClient

Manual Testing Checklist

Before submitting, verify:

  • The mod loads without errors (check the latest log).
  • Existing aliases still work correctly.
  • New features work as described in the issue or design.
  • Edge cases are handled (empty inputs, invalid parameters, permission denials).
  • Console/log output is clean (no unexpected error messages).

Cross-Version Compatibility

If your change affects a feature shared across multiple Minecraft versions, test it on at least the primary module (server-1.21) and one legacy module. Some Minecraft versions have different command syntax or NBT formats.

Submitting a Pull Request

Before You Submit

  1. Sync your fork with the upstream repository:
git checkout main
git pull upstream main
git checkout my-feature-branch
git rebase main
  1. Make sure your branch compiles and all existing features still work.
  2. Review your changes: git diff main...HEAD

Creating the PR

  1. Push your branch to your fork:
git push origin my-feature-branch
  1. Go to the Command Maker repository on GitHub.
  2. Click the Compare & pull request button that appears.
  3. Write a clear title and description:
    • Title: Short summary starting with a verb (e.g., "Add custom color picker to GUI").
    • Description: Explain what the change does, why it is needed, and how to test it.
    • Reference related issues with Closes #123 or Related to #456.
  4. Submit the pull request.

After Submitting

  • Be responsive to review feedback. Maintainers may ask for changes.
  • Make requested changes on your branch; the PR updates automatically.
  • Once approved, a maintainer will merge your PR.
  • Celebrate your contribution!

Pull Request Review Process

Stage What Happens Typical Duration
Submitted PR is created and automated checks run Minutes
Initial Review Maintainer reviews for obvious issues 1-3 days
Code Review Detailed review of logic, style, and architecture 3-7 days
Changes Requested You address feedback and update the PR Varies
Approved PR is accepted and merged 1-2 days after final review

Community Guidelines

  • Be respectful: All contributions are welcome, and everyone should feel safe to participate.
  • Be constructive: Focus on the code, not the person. Suggest improvements rather than just pointing out flaws.
  • Be patient: Maintainers are volunteers and may take time to review your contribution.
  • Ask for help: If you are stuck, open a discussion or ask on the issue tracker. The community is happy to help.

Do Not

  • Submit PRs that introduce breaking changes without prior discussion.
  • Modify versions or dependencies without a clear reason.
  • Commit generated files, IDE configuration files, or local settings.
  • Bypass the pull request process by pushing directly to main.

Documentation Contributions

Documentation is maintained in the docs/ directory as HTML files. To contribute documentation:

  1. Find or create an issue for the documentation topic.
  2. Follow the same fork/branch/PR workflow.
  3. Match the style of existing documentation pages (use the same HTML skeleton and CSS classes).
  4. Use callout-info, callout-warning, callout-tip, and callout-danger for emphasis boxes.
  5. Include practical examples wherever possible.

Getting Help

If you need assistance at any point:

  • GitHub Issues: Ask questions or report problems on the issue tracker.
  • Discord: Join the community Discord for real-time discussion.
  • Wiki: Check the existing wiki pages for documentation on specific features.

Thank you for contributing to Command Maker! Every contribution, no matter how small, helps make the project better for everyone.
