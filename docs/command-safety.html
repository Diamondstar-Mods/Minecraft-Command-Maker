Command Safety

Command Maker gives you enormous power to create aliases and automate server actions. With great power comes great responsibility. This guide covers the dangers to watch out for and how to create safe, reliable aliases.

Read This First

Creating unsafe aliases can crash your server, corrupt worlds, give unintended OP access, or ruin player experiences. Always test new aliases in a single-player world or a test server before deploying to a live server. The few minutes it takes to test can save hours of recovery work.

Danger 1: OP and Gamemode Commands in Aliases

Putting OP-level commands like op, gamemode creative, or setblock into an alias without permission restrictions is one of the most dangerous things you can do.

Risky Examples

// DANGEROUS - Never create these without permission checks
"make_admin": "op ${player}"
"creative": "gamemode creative ${player}"
"give_diamond": "give ${player} diamond_block 64"
"summon_wither": "summon minecraft:wither ~ ~ ~"

If any player can run /make_admin, they can OP themselves and take over your server. Even /creative without restrictions lets anyone switch to creative mode and bypass survival protections.

Safe Approach

{
  "permissions": {
    "ServerOwner": "ADMIN"
  },
  "alias_permissions": {
    "make_admin": "ADMIN",
    "creative": "MODERATOR",
    "give_diamond": "MODERATOR"
  }
}

Always restrict dangerous aliases to the highest permission level needed. See the Permissions Setup guide for detailed instructions.

Danger 2: Execute as @p Risks

Using @p (nearest player) in aliases can have unintended consequences when multiple players are near each other:

// RISKY: What if the wrong player is nearest?
"kill_nearest": "execute as @p run kill @s"
"tp_them": "tp @p 0 100 0"

How @p Goes Wrong

If you type /kill_nearest while standing next to another player, @p might target them instead of you. Always prefer @s (self) when you mean the command sender. Use @p only when you explicitly intend to target the nearest other entity and have considered the edge cases.

Safer Alternatives

// SAFE: Uses the executing player
"kill_self": "kill @s"
"tp_self": "tp @s 0 100 0"

// SAFER with @p: Clearer intent and feedback
"tp_to_player": "execute at @p run tp @s @p && say Teleported to nearest player."

Danger 3: Infinite Recursion

An alias that calls itself creates an infinite loop that can freeze or crash the server. This can happen directly or through a chain of aliases:

Direct Recursion

// DANGEROUS: Calls itself infinitely
"loop": "loop"

// Also dangerous: calls itself through another command
"say_hi": "say_hi ${player}"

Indirect Recursion (Chain)

// file: a.mcfunction
b

// file: b.mcfunction
c

// file: c.mcfunction
a  ← loops back to a!

Command Maker does not have built-in recursion protection. The server's command limit will eventually stop the execution, but by that point, the server may have processed thousands or millions of commands, causing severe lag or a crash.

Loop Detection Tips

If your server suddenly lags after you run a new alias:

  • Check server console for rapidly repeating command output
  • Check your most recently created aliases for self-references
  • Check function chains for circular references between .mcfunction files
  • Use /kill @s if you can still type commands to end the loop for your player
  • As a last resort, kill the server process from your host's control panel

Danger 4: Dangerous Target Selectors

Using broad target selectors like @a (all players), @e (all entities), or @r (random player) with destructive commands can cause massive damage:

Selector Targets Risk Level
@s Self only Safe
@p Nearest player Low (but context-dependent)
@r Random player Medium
@a All players High with destructive commands
@e All entities Very High

Devastating Examples

// EXTREMELY DANGEROUS - Never create these
"kill_all": "kill @e"                // Kills ALL entities including item frames, armor stands, paintings
"ban_all": "ban @a"                  // Bans every player on the server
"clear_inventory": "clear @a"        // Clears every player's inventory
"random_kick": "kick @r"             // Kicks a random player (could be you!)
"explode_all": "execute as @e at @s run summon minecraft:tnt ~ ~ ~"  // TNT at every entity

The @e Trap

@e targets every entity in the world, not just players. This includes item frames, paintings, minecarts, boats, armor stands, dropped items, arrows, and experience orbs. A kill @e command can destroy all decorations, storage systems using item frames, and remove all dropped items from the ground. If you mean to target only players, use @a. If you mean to target only yourself, use @s.

Protecting Sensitive Aliases with Permissions

Every alias that performs a destructive or privileged operation must be protected by permissions. Here is a categorization of alias risk levels:

Risk Level Command Types Required Permission
Safe say, tellraw, title, playsound, weather, time set ALIAS_USER (default)
Low Risk tp @s, effect give @s, give @s, spawnpoint ALIAS_USER
Medium Risk tp <other>, gamemode, effect give @a, difficulty COMMAND_USER
High Risk ban, kick, kill @e, clear @a, setblock, fill MODERATOR
Critical op, deop, stop, save-all, pardon, whitelist ADMIN

Principle of Least Privilege

Grant the minimum permission level needed for each alias. A command that displays server info needs ALIAS_USER, not ADMIN. This principle limits damage from mistakes and makes your server more secure. You can always raise a permission later, but you can't undo a server crash.

The Safe Alias Checklist

Before deploying any alias to a live server, go through this checklist:

  1. Does the alias use @e or @a?
    If yes, can you replace it with @s or a more specific selector?
  2. Does the alias modify world state?
    Commands like fill, setblock, clone can damage builds.
  3. Does the alias affect other players?
    Commands like kick, ban, kill, tp targeting others need permission restrictions.
  4. Could the alias loop infinitely?
    Check for self-references and circular function chains.
  5. Is the permission level correct?
    Set the minimum level in alias_permissions that can safely use this command.
  6. Does the alias use syntax parameters?
    Verify that user-provided parameters are validated or used safely.
  7. Does the alias provide user feedback?
    Good aliases tell the user what happened. Silent failures can hide problems.
  8. Have you tested the alias?
    Test on a single-player world or test server first. Test with a non-OP account to verify permissions work.

Printable Checklist

Copy these checklist items into a text file or document. Run through them for every new alias, especially ones that use @e, @a, destructive commands, or syntax parameters from user input.

Testing in a Safe Environment

Always follow this testing workflow before deploying a new alias to production:

Stage 1: Single-Player World

  1. Create a backup of your test world
  2. Test the raw command directly in chat first (without Command Maker)
  3. If the raw command works, create the alias
  4. Test the alias as an OP player
  5. Verify the output is what you expect
  6. Check for side effects (did something unexpected happen?)

Stage 2: Test Server

  1. Install the alias on a test server with the same configuration as production
  2. Test with a non-OP account to verify permission restrictions
  3. Have another player test the alias simultaneously to check for multiplayer issues
  4. Monitor server console for errors
  5. Test edge cases: empty parameters, very long inputs, special characters

Stage 3: Production

  1. Announce the new alias to players
  2. Monitor closely for the first hour after deployment
  3. Have a rollback plan: know how to quickly disable or fix the alias

Backup Before Testing

Always back up your world before testing new aliases, especially ones that use fill, clone, setblock, kill, or clear. A single wrong coordinate can destroy hours of building. On a server, use /save-off and /save-on to control when changes are written to disk during testing.

Quick Reference: Safe Patterns

Pattern Safe? Notes
say ${message} Safe Read-only, no world impact
tp @s 0 100 0 Safe Only affects the executor
give @s diamond 1 Safe with permission Restrict to avoid item farms
kill @e[type=creeper] Conditional Safe if properly scoped; dangerous if too broad
fill ~ ~ ~ ~10 ~10 ~10 air Risky Can destroy builds; use relative coords carefully
ban ${player} Needs MODERATOR+ Always require high permission level
op ${player} Needs ADMIN only Never make this available to regular players
stop Needs ADMIN only Shuts down the server immediately
kill @e Extremely Dangerous Never use without specific type filter and MODERATOR+ permission
