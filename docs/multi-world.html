Multi-World Setups

Running a server with multiple worlds or dimensions introduces unique challenges for command configuration. This guide covers strategies for making Command Maker work seamlessly across different worlds.

Understanding Dimensions in Minecraft

Minecraft has three primary dimensions: Overworld, Nether, and The End. Multi-world plugins (like Multiverse-Core or similar) can create additional worlds. Each world or dimension has a unique identifier that you can use in your aliases.

Dimension / World Internal Identifier Minecraft Command Prefix
Overworld minecraft:overworld execute in minecraft:overworld
Nether minecraft:the_nether execute in minecraft:the_nether
The End minecraft:the_end execute in minecraft:the_end
Custom world file:world_name execute in file:world_name

Dimension Detection with ${dimension}

Using the ${dimension} Variable

Command Maker provides a built-in variable ${dimension} that resolves to the identifier of the dimension the player is currently in. This is invaluable for creating dimension-aware aliases.

# Tell the player where they are
/cmd add whereami say You are in: ${dimension}

# Example outputs:
# "You are in: minecraft:overworld"
# "You are in: minecraft:the_nether"
# "You are in: minecraft:the_end"

Dimension-Aware Teleportation

Teleportation across dimensions requires the execute in command. Use ${dimension} to create context-sensitive teleports:

# Safe spawn teleport that works in any dimension
/cmd add spawn execute in minecraft:overworld run tp ${player} 0 65 0

# Return to your previous dimension after visiting the End
/cmd add back execute in ${dimension} run tp ${player} ${x} ${y} ${z}

Conditional Commands Based on Dimension

Use execute if to create dimension-specific behavior:

/cmd add heal execute if entity @s[nbt={Dimension:"minecraft:overworld"}] run effect give @s instant_health 1

# Or more practically, use the dimension in /execute commands:
/cmd add top execute if dimension minecraft:overworld run tp ${player} ~ 256 ~
/cmd add top execute if dimension minecraft:the_nether run tp ${player} ~ 128 ~

World-Specific Aliases

Why World-Specific Aliases Matter

A command that makes sense in the Overworld might be dangerous or useless in the Nether. For example, a /spawn command should always send players to the Overworld spawn point, and /sethome should store which dimension the home is in.

Example: Dimension-Aware Home System

{
  "sethome": "execute store result score ${player} homeDim run data get entity @s Dimension && say Home set for ${dimension}!",
  "home": "execute if score ${player} homeDim matches 0 run tp @s 0 65 0 && execute if score ${player} homeDim matches -1 run tp @s 0 65 0"
}

Pro Tip

Combine ${dimension} with scoreboard tracking to build a complete cross-dimensional home or warp system. Store not just coordinates, but also the dimension ID for each home point.

Separate Configs Per World

Current Limitations

Command Maker uses a single set of configuration files (aliases.json, syntax.json, etc.) for all worlds. There is no built-in per-world configuration separation. However, you can achieve similar results through careful alias design.

Approach 1: Prefix Aliases by World

// Overworld-specific commands
/ow_spawn: execute in minecraft:overworld run tp ${player} 0 65 0
/ow_time: execute in minecraft:overworld run time set day

// Nether-specific commands
/net_spawn: execute in minecraft:the_nether run tp ${player} 0 65 0
/net_time: execute in minecraft:the_nether run time set day

// End-specific commands
/end_spawn: execute in minecraft:the_end run tp ${player} 0 65 0

Approach 2: Unified Aliases with Dimension Detection

/spawn: execute in minecraft:overworld run tp ${player} 0 65 0 && say Teleported to Overworld spawn!

/setspawn: execute if dimension minecraft:overworld run setworldspawn ~ ~ ~
/setspawn: execute if dimension minecraft:the_nether run say Cannot set world spawn in the Nether!

Approach 3: Warp Points with Dimension

// Store warp coordinates with dimension in a custom variable
/setcmdvariable warp_lobby_coords "0 65 0"
/setcmdvariable warp_lobby_dim "minecraft:overworld"
/setcmdvariable warp_mining_coords "1000 50 -500"
/setcmdvariable warp_mining_dim "minecraft:overworld"

// Create warp aliases
/cmd add warp_lobby execute in minecraft:overworld run tp ${player} ${warp_lobby_coords}
/cmd add warp_mining execute in minecraft:overworld run tp ${player} ${warp_mining_coords}

Multi-Server Setups

Proxy Networks (BungeeCord / Velocity)

If your server network uses a proxy (BungeeCord, Velocity, or similar) to link multiple servers, Command Maker runs independently on each server. This means aliases must be configured separately on each backend server.

# Example: Lobby server aliases
/lobby_help: say Available: /survival, /creative, /minigames
/survival: say Connecting to survival server...
/creative: say Connecting to creative server...

# Example: Survival server aliases
/spawn: tp ${player} 0 65 0
/home: tp ${player} ${home_coords}
/tpa: tellraw ${tpa_player} {"text":"TPA request from ${player}"}

Synchronizing Configs Between Servers

Keeping configurations consistent across multiple servers can be challenging. Here are several approaches:

Method Difficulty Reliability Best For
Manual copy Easy Low (human error) 2-3 servers, infrequent changes
Shared network drive Medium High Servers on same machine or LAN
Git-based sync Medium Very High Teams, versioned configs
rsync / Sync scripts Medium High Linux servers, automation
Configuration management (Ansible, Salt) Advanced Very High Large networks, DevOps approach

Git-Based Sync Example

# On the master configuration server
cd /opt/commandmaker-config
git init
git add .
git commit -m "Initial config"

# On each game server (run as cron job every 5 minutes)
#!/bin/bash
cd /path/to/server/config/CommandMaker
git pull origin main  # Pull latest configs
/cmd reload            # Reload in-game (via server console command)

Syncing Configs Between Servers

Option 1: Shared Storage (NFS / SMB)

# Mount a shared NFS drive on each game server
mkdir -p /mnt/commandmaker-config
mount -t nfs master-server:/export/commandmaker /mnt/commandmaker-config

# Symlink the config directory
ln -sf /mnt/commandmaker-config /path/to/server/config/CommandMaker
# Then /cmd reload on each server after changes

Option 2: Automated Sync Script

#!/bin/bash
# sync-commandmaker.sh - Run on each game server

MASTER_SERVER="config-master.example.com"
CONFIG_PATH="/path/to/server/config/CommandMaker"

# Pull the latest config
rsync -avz --delete "${MASTER_SERVER}::commandmaker/" "$CONFIG_PATH/"

# Notify the server (requires server management tooling)
echo "Configuration synced from ${MASTER_SERVER}"

Option 3: Plugin-Based Sync

Some server management plugins support file synchronization. Check if your hosting panel or server management tool supports custom file sync rules for the config/CommandMaker/ directory.

Important

Always run /cmd reload after syncing configuration files. Command Maker will not automatically detect file changes -- it uses the cached configuration until explicitly reloaded.

Best Practices for Multi-World Setups

  • Use execute in for cross-dimensional commands to ensure they run in the correct dimension
  • Test aliases in each world before deploying to production
  • Prefix world-specific aliases to avoid confusion (e.g., /survival_spawn, /creative_spawn)
  • Document per-world behavior in your server's help system
  • Keep a master copy of configuration files in a central location
  • Use version control for configuration files when managing multiple servers
  • Consider a unified /help alias that shows commands relevant to the current world

Example: Complete Multi-World Teleport Hub

// === TELEPORT HUB FOR MULTI-WORLD SERVER ===

// Set warp points
/setcmdvariable warp_spawn "0 65 0"
/setcmdvariable warp_survival "1000 65 0"
/setcmdvariable warp_mining "2000 50 -500"
/setcmdvariable warp_creative "3000 65 0"
/setcmdvariable warp_minigames "4000 65 0"

// Create warp aliases
/cmd add spawn execute in minecraft:overworld run tp ${player} ${warp_spawn}
/cmd add survival execute in minecraft:overworld run tp ${player} ${warp_survival}
/cmd add mining execute in minecraft:overworld run tp ${player} ${warp_mining}
/cmd add creative execute in minecraft:overworld run tp ${player} ${warp_creative}
/cmd add games execute in minecraft:overworld run tp ${player} ${warp_minigames}

// Help command showing only relevant warps
/cmd add help say === Teleport Hub ===
/cmd add help say /spawn - Return to spawn
/cmd add help say /survival - Survival world
/cmd add help say /mining - Mining world
/cmd add help say /creative - Creative world
/cmd add help say /games - Minigames world

// Dimension check aliases
/cmd add whereami say You are currently in: ${dimension}

// Cross-dimensional return
/cmd add lobby execute in minecraft:overworld run tp ${player} ${warp_spawn}

Note

Multi-world functionality depends heavily on your server setup. Vanilla Minecraft supports three dimensions. Third-party plugins add more worlds. Always verify dimension identifiers for your specific server configuration by running /whereami (using the alias above).
