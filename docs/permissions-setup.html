Permissions Setup

Configure who can use which commands on your server. Command Maker provides a flexible permission system that works out of the box, with optional support for LuckPerms integration.

Understanding Permission Levels

Command Maker uses a hierarchical permission system with five levels. Each level includes all permissions of the levels below it.

Level Value Allowed Actions Typical Users
NONE 0 No Command Maker commands Default / unassigned players
ALIAS_USER 1 Run aliases and functions Regular players
COMMAND_USER 2 All alias/functions usage, use /cmd to view info Trusted players, helpers
MODERATOR 3 Add and delete aliases, manage permissions, reload config Moderators, staff
ADMIN 4 Full access to all Command Maker features Server admins, owners

How Permission Resolution Works

Command Maker checks permissions in this order: (1) LuckPerms if installed and the player has a cmmaker.* permission node, (2) Opped players get ADMIN by default, (3) Falls back to permissions.json file, (4) If no permission is set, defaults to ALIAS_USER. This means you only need to configure permissions for players who should be restricted.

Creating permissions.json

The permissions.json file lives in config/CommandMaker/ and defines player permissions and per-alias access restrictions.

Basic Structure

{
  "permissions": {
    "Steve": "ADMIN",
    "Alex": "MODERATOR",
    "BuilderBob": "COMMAND_USER",
    "GuestPlayer": "ALIAS_USER"
  },
  "alias_permissions": {}
}

This assigns permission levels to specific players by their Minecraft username. Player names are case-sensitive, so "Steve" and "steve" are treated as different players.

Using UUIDs (Recommended)

For servers where player names might change, use UUIDs instead of usernames. This ensures permissions persist through name changes:

{
  "permissions": {
    "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx": "ADMIN",
    "yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy": "MODERATOR"
  },
  "alias_permissions": {}
}

Finding Player UUIDs

You can find a player's UUID by running /data get entity <player> UUID in-game, or by using an online tool like MCUUID. You can mix UUIDs and usernames in the same file.

Assigning Per-Alias Permissions

The alias_permissions section lets you restrict specific aliases to certain permission levels. This is essential for protecting dangerous commands while letting regular players use harmless ones.

Restrict by Minimum Level

{
  "permissions": {
    "Steve": "ADMIN",
    "Alex": "MODERATOR"
  },
  "alias_permissions": {
    "ban": "MODERATOR",
    "kick": "MODERATOR",
    "stop": "ADMIN",
    "broadcast": "COMMAND_USER",
    "spawn": "ALIAS_USER",
    "home": "ALIAS_USER"
  }
}

In this example:

  • /ban and /kick require at least MODERATOR level
  • /stop requires ADMIN level
  • /broadcast requires COMMAND_USER (trusted players)
  • /spawn and /home are available to anyone with ALIAS_USER or higher

Always Protect Destructive Commands

Any alias that can ban, kick, stop, kill, op, gamemode, setblock, or fill should have a permission restriction. Never leave commands like /stop or /ban accessible to all players. See the Command Safety guide for more details.

Using Wildcards

Wildcards let you group permissions by prefix patterns, which is useful when you have many related aliases. Command Maker supports the asterisk (*) wildcard character.

Prefix-Based Wildcards

{
  "permissions": {},
  "alias_permissions": {
    "admin_*": "ADMIN",
    "mod_*": "MODERATOR",
    "staff_*": "COMMAND_USER",
    "player_*": "ALIAS_USER"
  }
}

With this setup, any alias starting with admin_ (like /admin_stop, /admin_restart) requires ADMIN level. Aliases starting with mod_ require MODERATOR level, and so on. Aliases that don't match any pattern default to the player's base permission level.

Wildcard Overrides

You can override a wildcard with a specific alias permission. More specific rules take precedence over wildcards:

{
  "permissions": {},
  "alias_permissions": {
    "admin_*": "ADMIN",
    "admin_help": "ALIAS_USER"
  }
}

Here, /admin_help is accessible to all ALIAS_USER players, even though other admin_* commands are restricted to ADMIN. The explicit entry overrides the wildcard.

Testing Permissions

After configuring permissions, follow these steps to verify everything works correctly:

  1. Reload the configuration: 
    /cmd reload
    Always reload after editing permissions.json for changes to take effect.
  2. Test as a regular player: Log in with a non-oppped account or use /deop <player> to simulate a non-admin user. Try running restricted aliases and verify they are blocked.
  3. Check the permission error message: Players without sufficient permission will see a message like "You do not have permission to use this alias." If you see a different error, the alias itself may have a syntax issue.
  4. Verify inherited permissions: Make sure a MODERATOR can still use ALIAS_USER-level commands. The hierarchy should cascade downward.
  5. Test wildcard matching: Create test aliases with different prefixes and verify the correct permission level is enforced.

Test Before Players Are Online

Always test permission changes in a safe environment before applying them to a live server. A misconfigured permission file can accidentally expose dangerous commands or lock out legitimate staff members.

Common Permission Setups

Small Server (5-10 Players)

On small servers, a simple setup with admin and everyone-else works well:

{
  "permissions": {
    "ServerOwner": "ADMIN",
    "TrustedFriend": "MODERATOR"
  },
  "alias_permissions": {
    "stop": "ADMIN",
    "restart": "ADMIN",
    "kick": "MODERATOR",
    "mute": "MODERATOR"
  }
}

Unlisted players default to ALIAS_USER, so they can use basic commands like /spawn, /home, and /tpa without any additional configuration.

Large Server (50+ Players)

Larger servers benefit from a structured permission ladder with clear role separation:

{
  "permissions": {
    "Owner": "ADMIN",
    "Admin1": "ADMIN",
    "Admin2": "ADMIN",
    "Moderator1": "MODERATOR",
    "Moderator2": "MODERATOR",
    "Helper1": "COMMAND_USER",
    "Helper2": "COMMAND_USER",
    "VIP_Player": "ALIAS_USER"
  },
  "alias_permissions": {
    "stop": "ADMIN",
    "restart": "ADMIN",
    "saveall": "ADMIN",
    "sudo": "ADMIN",
    "ban": "MODERATOR",
    "kick": "MODERATOR",
    "mute": "MODERATOR",
    "warn": "MODERATOR",
    "tempban": "MODERATOR",
    "broadcast": "COMMAND_USER",
    "freeze": "MODERATOR",
    "tp": "COMMAND_USER",
    "tphere": "COMMAND_USER",
    "vip_*": "ALIAS_USER"
  }
}

Server with LuckPerms

If you use LuckPerms, you can manage all permissions through LuckPerms groups instead of permissions.json. The permissions.json file can remain empty or be omitted entirely:

{
  "permissions": {},
  "alias_permissions": {
    "stop": "ADMIN",
    "ban": "MODERATOR"
  }
}

Player permissions are then assigned via LuckPerms permission nodes. See the LuckPerms Integration guide for detailed setup instructions.

Permission Fallback Chain

Understanding the fallback chain is important for troubleshooting permission issues:

Priority Source Checked
1 (Highest) LuckPerms cmmaker.* nodes If LuckPerms is installed and player has matching nodes
2 Vanilla OP status Opped players automatically get ADMIN
3 permissions.json player entry If player is listed with a permission level
4 (Lowest) Default permission ALIAS_USER for all unlisted players

Permission Check Short-Circuit

Command Maker checks sources in order and stops at the first match. If LuckPerms is installed and returns a result for a player, OP status and permissions.json are not checked for that player. This means you can use permissions.json as a fallback for servers where LuckPerms is installed but not configured for every player.

Removing Permissions

To remove a player's special permissions and let them fall back to the default level:

  • Delete their entry from the permissions section of permissions.json
  • Or set their level to ALIAS_USER (the default)
  • Run /cmd reload to apply changes
